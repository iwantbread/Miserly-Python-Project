## 1. What you have actually built

The current project is the **authentication component** of a business tracking web application. Authentication means checking who a user is. It provides registration, login, a page that requires login, and logout. The dashboard is a placeholder where the team can add business tracking features.

The ZIP supplied with the task had UI filenames but empty UI implementations. There was no existing design to copy, so the app uses a simple green design.

Three things cooperate:

| Part | Runs where? | Responsibility |
| --- | --- | --- |
| Browser | User's computer | Shows HTML, applies CSS, and sends forms |
| Python + Flask | Server computer; currently your own computer | Receives requests, checks input/passwords, chooses responses |
| SQLite | Database file accessible to the Python process | Stores user accounts persistently |

During local development the browser and server happen to run on the same laptop. They still communicate as separate programs using HTTP. On a deployed website the server would normally be another machine.

The browser does **not** receive `main.py`, the password hash database, or the secret key file. It receives the HTML generated by templates, CSS, and HTTP headers/cookies. Anything sent to the browser, including hidden inputs, is visible to its user.

## 2. What Flask is, and why these tools were chosen

**Python** is the programming language. **Flask** is a web framework written for Python: a package that supplies useful building blocks for handling web requests and producing web responses. Our code tells Flask which functions should handle which URLs and how to process the forms. Flask is installed into the project's virtual environment.

For example:

```python
@app.route('/dashboard')
def dashboard():
    return render_template('dashboard.html')
```

This associates a URL path with a Python function. Flask calls the function when the relevant request arrives. The function's result becomes the HTTP response. The real dashboard also has a login protection decorator, explained later.

Flask is called a **microframework** because its core stays relatively small and lets the application choose extra pieces. It does not mean the resulting application must be tiny. We use a small amount of direct SQL rather than adding an ORM (a system that maps database records to Python objects). This keeps this assignment's database operations visible.

| Tool | What it contributes | Why it fits this project |
| --- | --- | --- |
| Flask | Routing, request/response helpers, sessions, template integration | Required by the assignment; enough for this feature |
| Jinja | Template language used through Flask | Inserts user information and reuses a shared page layout |
| Werkzeug | Web utilities used by Flask; password hashing/checking helpers used directly here | Avoids inventing a password storage algorithm |
| SQLite / `sqlite3` | Database engine / Python interface to it | Persistent storage without setting up a separate database server |
| HTML | Browser document structure and forms | Defines labels, inputs, buttons, links, and page structure |
| CSS | Browser presentation rules | Gives the app its colours, spacing, layout, and responsive behaviour |
| `unittest` | Python's standard testing framework | Tests the authentication routes without another test dependency |
| `venv` and `pip` | An isolated Python environment and package installation | Keeps this project's dependencies separate |

There is no JavaScript in this implementation. Normal HTML forms and browser navigation are enough for the current features. Python produces HTML on the server; CSS is applied by the browser. JavaScript could be added later for behaviour such as updating part of a page without a full reload.

Flask's dependencies also install packages such as Jinja2, MarkupSafe (safe HTML escaping support), ItsDangerous (signing support), Click (command-line support), and Blinker (signals). These are supporting dependencies, not additional frameworks you wrote. Their exact installed versions can differ because `requirements.txt` specifies a compatible version range.

See the official [Flask introduction](https://flask.palletsprojects.com/en/stable/quickstart/) for the framework's minimal application example.

## 3. Web terms you need before reading the code

### URL, server, port, request, response

In `http://127.0.0.1:5000/login`:

| Piece | Meaning |
| --- | --- |
| `http` | The communication protocol |
| `127.0.0.1` | Loopback address: this same computer |
| `5000` | Port: the local network endpoint where the app listens |
| `/login` | Path: which resource/route you want |

The browser sends an HTTP **request**. Flask dispatches it to a route function, which produces an HTTP **response**. A response has a status, headers, and usually a body such as HTML. A cookie is sent using headers, not an HTML input.

### GET and POST

**GET** asks for a page or resource. Typing `/login` into the address bar makes a GET request. **POST** submits data for processing. Submitting the login form makes a POST request to `/login`.

Using POST does not encrypt a password. HTTPS is what protects traffic in transit. Our localhost demonstration uses HTTP; a real deployment needs HTTPS.

Routes that only render a page use GET. Registration/login accept GET to display their form and POST to process it. Logout changes the session, so it accepts POST rather than an ordinary GET link.

| Status used by this app | Meaning |
| --- | --- |
| `200` | A page was successfully returned, including a form redisplayed with an error |
| `302` | Redirect: the browser should make another request to the given location |
| `400` | Bad request: the POST failed the CSRF check |
| `405` | Method not allowed, for example GET `/logout` |

### Database, session, and `g` are different

| Storage | Typical contents here | Lifetime and location |
| --- | --- | --- |
| SQLite database | User ID, name, email, password hash | Server-side disk file; persists after shutdown |
| Flask `session` | `user_id`, CSRF token, temporary messages | Default Flask implementation uses a signed browser cookie; carried between requests |
| Flask `g` | Current database connection, current user row | Attached to the current application context, normally one request |

The name `g` is short for a context-local namespace, often described as a place for request-related data. It is **not** a single global user shared by everybody. Each normal request has its own context.

The default Flask cookie is **signed, not encrypted**. Its holder can read its data. The signature allows the server to detect modification without the secret key. We store a user ID rather than a password there. Editing the cookie to claim another user ID does not give a valid signature.

The cookie is how the browser brings session data back. On each request the app uses its authenticated user ID to look up the user's current database row. The app does not repeatedly ask the user for a password.

The official [Flask sessions documentation](https://flask.palletsprojects.com/en/stable/quickstart/#sessions) explains this cookie signing model.

## 4. Essential Python syntax used throughout

Read the following as a reference. The line-by-line walkthrough then applies these ideas to your actual code.

| Syntax | Meaning | Example |
| --- | --- | --- |
| `=` | Assign a value to a name or entry | `error = None` |
| `==` | Compare values for equality | `request.method == 'POST'` |
| `!=` | Compare values for inequality | `password != confirmation` |
| `is None` | Check specifically for the singleton representing no value | `error is None` |
| `'text'`, `"text"` | Strings; both quoting styles work | `'login'` |
| `True`, `False` | Boolean values; capitalised in Python | `registering=True` |
| `None` | No value / no result | No matching database row |
| `thing.member` | Access an attribute or method | `request.method`, `file.write` |
| `function(...)` | Call a function | `len(password)` |
| `object.method(...)` | Call a function attached to an object | `email.lower()` |
| `items['key']` | Retrieve a mapping entry by key | `session['user_id']` |
| `items.get('key', default)` | Retrieve an entry, or the default if absent | `request.form.get('name', '')` |
| `{}` | Empty dictionary, a key/value mapping | No test overrides |
| `{'name': 'Sam'}` | Dictionary with one entry | A test configuration or form |
| `['GET', 'POST']` | List containing two values | Allowed HTTP methods |
| `(a, b)` | Tuple, an ordered collection | SQL parameter values |
| `(a,)` | One-element tuple; comma is essential | One SQL parameter |
| `[-1]` | Last element of a sequence | Domain after splitting an email |
| `not`, `and`, `or` | Logical operations with short-circuit evaluation | Check conditions |
| `in`, `not in` | Membership test | `'csrf_token' not in session` |
| `:` then indentation | Start a block | Functions, `if`, `with`, `try` |
| `return value` | Stop this function and give its caller a result | Return HTML or a redirect |
| `pass` | Intentionally do nothing in this block | Existing key file is acceptable |

Python uses indentation to determine which statements belong together. This project uses four spaces per level. Blank lines do not end a block; decreasing indentation does.

```python
if password == 'example':
    print('Inside the conditional block')
print('Outside the conditional block')
```

In an expression like `if user:`, Python tests **truthiness**. `None`, `''`, and empty collections are false-like. A normal database user row is true-like. `if not name:` therefore catches an empty name.

`and` stops at a false-like part; `or` stops at a true-like part. This matters for safety as well as brevity. If `user` is `None`, `user and check_password_hash(...)` does not try to access `user['password_hash']`.

Functions are objects in Python: they can be stored, passed as arguments, and returned. `csrf_token` refers to a function; `csrf_token()` calls it. That difference is central to decorators and template helpers.

### Lines 11–12: create the application

```python
def create_app(test_config=None):
    app = Flask(__name__, instance_relative_config=True)
```

**Line 11:** `def` defines a function called `create_app`. `test_config` is a parameter. `=None` makes it optional; if the caller supplies nothing, its value is `None`. Defining the function does not run its body. `create_app()` later calls it.

This is an **application factory**: a function that builds and returns an application. Tests can ask it for an app connected to a temporary database; normal execution asks it for the real app. This avoids starting the real server merely because a test imports the module.

**Line 12:** `Flask(...)` constructs an object of the `Flask` class and assigns it to `app`. Think of the object as the configured application, including its routes and settings.

`__name__` is a special variable Python sets for each module. Flask uses the module identity to locate application resources. `instance_relative_config=True` makes relative configuration file loading use the instance directory; it does not itself load a configuration file. Our database location is separately built from `app.instance_path` below.

The functions inside `create_app` are **nested functions**. They can access `app` from the surrounding function. That retained access is a **closure**. Flask keeps references to registered functions, so they still work after `create_app` returns.

### Lines 13–17: configuration

```python
app.config.from_mapping(SECRET_KEY=os.environ.get('SECRET_KEY'),
                        DATABASE=str(Path(app.instance_path) / 'miserly.sqlite'),
                        SESSION_COOKIE_HTTPONLY=True, SESSION_COOKIE_SAMESITE='Lax',
                        MAX_CONTENT_LENGTH=16384)
app.config.update(test_config or {})
```

`app.config` is a mapping of setting names to values. `.from_mapping(...)` adds these defaults. Python allows a function call to continue across physical lines while its parentheses remain open. These four source lines are one call.

**Line 13:** `SECRET_KEY=...` is a **keyword argument** to the call, not an equality test. `os.environ` contains environment variables. `.get('SECRET_KEY')` returns the configured string or `None` if missing. This key signs session cookies. It is not the database password or the user's password hash.

**Line 14:** `Path(app.instance_path)` creates a path object. `/ 'miserly.sqlite'` joins a filename to the directory. Here `/` is the path object's join operator, not numeric division. `str(...)` converts the result to a string for the database configuration. The database is inside `instance/`.

**Line 15:** `SESSION_COOKIE_HTTPONLY=True` tells browsers not to expose this cookie through ordinary JavaScript cookie access. `SESSION_COOKIE_SAMESITE='Lax'` restricts cookie sending in some cross-site situations. These are supporting protections; they do not encrypt a cookie or replace CSRF checks. `SESSION_COOKIE_SECURE` is not enabled here, because local development uses HTTP. A deployment needs HTTPS and the Secure cookie setting.

**Line 16:** `MAX_CONTENT_LENGTH=16384` limits request bodies to 16,384 bytes (16 KiB). The small forms do not need large uploads. Flask normally rejects an oversized body with a 413 response when enforcing this limit.

**Line 17:** `.update(...)` applies any settings supplied by the caller, overriding defaults. `test_config or {}` means “use the supplied mapping if truthy; otherwise use an empty dictionary.” It permits tests to pass their own database path, signing key, and testing flag. Calling `.update({})` changes nothing.

### Lines 18–26: create the private directory and development signing key


**Line 18:** `.mkdir()` creates the directory. `parents=True` permits creation of missing parent directories. `exist_ok=True` makes an already existing directory acceptable. This is why the app can start without you creating `instance/` manually.

**Line 19:** Run this block only when no truthy secret key has been configured.

**Line 20:** Build the path of the local key file. `key` is a `Path` object here, not yet the secret string.

**Line 21:** `try` starts code that may raise an exception, a signal that something went wrong.

**Line 22:** `.open('x')` creates a file exclusively. If that file already exists, Python raises `FileExistsError` rather than overwriting it. `with ... as file` is a **context manager**: it binds the opened file to the name `file` and closes it when the block ends, even if writing raises an error.

**Line 23:** `secrets.token_hex(32)` obtains 32 random bytes and represents them as 64 hexadecimal characters. `.write(...)` saves the string. This is a private randomly generated signing key.

**Lines 24–25:** `except FileExistsError` handles that specific exception. `pass` means do nothing: an existing key is what we want on later starts. Other errors, such as an unwritable directory, are not silently ignored.

**Line 26:** Read the key file and use its text as the application's secret. Keeping the same signing key allows the app to recognise previously signed cookies after a restart. Generate it once, not afresh on every launch. For deployment, provide `SECRET_KEY` through the environment and protect it.

The project uses `sqlite3` from Python's standard library. SQLite is embedded and needs no separate database service. See the official [Python SQLite introduction](https://docs.python.org/3/library/sqlite3.html#tutorial).

### Lines 40–42: initialise the user table

```python
with app.app_context():
    db().execute('CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL UNIQUE, password_hash TEXT NOT NULL)')
    db().commit()
```

**Line 40:** During startup we are not processing a browser request. Push an application context explicitly so the helper can use `g`. The `with` block removes that context when done, which also triggers the connection cleanup registered above.

**Line 41:** `db()` returns a connection; `.execute(...)` runs SQL. The text inside the quotes is SQL, not Python syntax. It declares a table if one does not already exist. Existing records are not deleted. It also does not update an old schema if the table's columns change later; that would need a database migration.

The SQL formatted for reading is:

```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL
)
```

| SQL part | Meaning |
| --- | --- |
| `users` | Table name: one row per user |
| `id INTEGER PRIMARY KEY` | Integer identifier unique to the row; SQLite supplies an ID when we omit it during insertion |
| `name TEXT NOT NULL` | A required text column |
| `email TEXT NOT NULL UNIQUE` | Required email text; two rows cannot have the same stored email |
| `password_hash TEXT NOT NULL` | Required text storing the password hash representation |

`NOT NULL` prevents SQL NULL values. It does not itself reject an empty string or validate an email. The Python validation handles those rules. Names are not unique: two people can share a name.

**Line 42:** `.commit()` commits the database transaction. Explicit commits are particularly important after inserts/updates so changes persist. SQLite/Python can manage some DDL details differently from inserts; the intention here is explicit initialisation completion.

### Lines 44–49: create and expose a CSRF token helper

```python
def csrf_token():
    if 'csrf_token' not in session:
        session['csrf_token'] = secrets.token_hex(32)
    return session['csrf_token']

app.jinja_env.globals['csrf_token'] = csrf_token
```

**Line 44:** Define a function templates will call to obtain the token.

**Lines 45–46:** If the session has no token yet, make an unpredictable random one and store it. Repeated renders in the same session reuse it rather than immediately invalidating other open forms.

**Line 47:** Return the token, which will be placed in a hidden form field.

**Line 49:** `app.jinja_env` is Flask's Jinja template environment. Its `globals` mapping exposes values/functions to templates. We place the **function object** there, so a template can call `{{ csrf_token() }}`. We do not call it here during app setup: there is no browser session to work with yet.

**CSRF** means cross-site request forgery: another website attempts to make a user's browser submit an unwanted action to our app. The browser may automatically send cookies, so the server also checks a token in the form. A different origin normally cannot read our page to extract its token. CSRF protection depends on browser origin protections and does not solve XSS or stolen sessions.

The hidden token is visible in page source. It is not a password or another login factor. A matching token proves that the submitted form has the token for this browser session; it does not prove a particular human's identity. The code gives this token no independent timeout.

### Lines 51–57: work performed before each route function

```python
@app.before_request
def load_user():
    g.user = db().execute('SELECT id, name, email FROM users WHERE id = ?', (session.get('user_id'),)).fetchone()
    if request.method == 'POST':
        token = session.get('csrf_token')
        if not token or not secrets.compare_digest(token, request.form.get('csrf_token', '')):
            return render_template('error.html'), 400
```

**Line 51:** Register a callback Flask runs before dispatching to the normal route function. This shares authentication setup and POST protection across routes rather than repeating it in every handler.

**Line 52:** Define that callback. Although named `load_user`, it also performs the CSRF check.

**Line 53:** This long line has several stages:

1. `session.get('user_id')` retrieves the logged-in ID, or `None` for an anonymous browser.
2. `(session.get('user_id'),)` is a **one-element tuple**. The comma makes it a tuple; `(value)` alone is just parentheses around a value.
3. SQL `SELECT id, name, email FROM users WHERE id = ?` asks for those columns of the matching user. It deliberately does not load the password hash for ordinary requests.
4. `?` is a parameter placeholder. SQLite receives the value separately, so it treats it as data rather than SQL code.
5. `.fetchone()` returns one row, or `None` if none matches.
6. Store that result in `g.user` for this request's routes and templates.

A session with no ID produces no matching row. A cookie whose user ID no longer exists in the database also produces no user and cannot pass the dashboard check.

**Line 54:** Only POST requests need this form token check in our current app. Displaying a page with GET continues without it. Future PUT/PATCH/DELETE routes would need an appropriate extension of this check.

**Line 55:** Retrieve the expected token from the signed session.

**Line 56:** Reject if the expected token is missing **or** the submitted token differs. `.get('csrf_token', '')` uses an empty string when the form field is missing. `secrets.compare_digest` is intended for comparing secret values without normal early-exit timing comparisons. `or` short-circuiting avoids calling it when no expected token exists.

**Line 57:** Return an error page and status 400. The comma forms a tuple `(body, status)`; Flask recognises that response format. Returning a response from `before_request` stops further route processing, so an invalid form never reaches the registration/login SQL.

If this callback reaches the end without a `return`, Python implicitly returns `None`. Flask interprets that as “continue processing.”

The error page's “expired” wording is general user-facing wording. The implementation does not track a separate form-expiry timestamp; a missing/mismatched token or a session change can cause this page.

### Lines 59–65: write a reusable login protection decorator

```python
def login_required(view):
    @wraps(view)
    def wrapped(*args, **kwargs):
        if g.user is None:
            return redirect(url_for('login'))
        return view(*args, **kwargs)
    return wrapped
```

**Line 59:** Define `login_required`, taking a function as the argument `view`. In web frameworks a **view function** is a request handler, not the screen itself. Here the decorator will receive `dashboard` or `logout`.

**Line 60:** `@wraps(view)` preserves the original function's name and other metadata on the wrapper. Flask normally uses the function name as the endpoint name. Without this, multiple protected functions could all appear to be called `wrapped`, causing endpoint-name conflicts.

**Line 61:** Define the wrapper, the function that will actually be called when the protected route is requested. `*args` collects positional arguments into a tuple. `**kwargs` collects keyword arguments into a dictionary. Our protected routes currently take no URL arguments, but this permits the decorator to forward arguments to future routes.

For example, `wrapped(7, mode='summary')` would receive `args == (7,)` and `kwargs == {'mode': 'summary'}`. In the later call `view(*args, **kwargs)`, the stars perform the reverse operation: unpacking those collections into arguments.

**Line 62:** Check the current request's user. `None` means no valid logged-in user was loaded.

**Line 63:** Build the login URL with `url_for('login')`, then return a redirect to it. `url_for` takes the **endpoint name**, not the literal filename or full URL. The browser receives a redirect and makes another request to `/login`. Returning here means the protected view's body is never called.

**Line 64:** If logged in, call the original function and return whatever it returns.

**Line 65:** Return the wrapper **function**, without calling it. The decorator's setup happens once when routes are defined; its login check happens separately on each protected request.

The following idea is roughly equivalent to using the decorator:

```python
# Teaching example, not an extra line in main.py:
dashboard = login_required(dashboard)
```

You pass the old function into `login_required` and receive a guarded function back.

### Lines 80–87: server-side validation

```python
if not name or len(name) > 80:
    error = 'Enter your name (up to 80 characters).'
elif len(email) > 254 or email.count('@') != 1 or not all(email.split('@')) or '.' not in email.split('@')[-1] or any(c.isspace() for c in email):
    error = 'Enter a valid email address.'
elif not 8 <= len(password) <= 128:
    error = 'Use a password between 8 and 128 characters.'
elif password != request.form.get('confirm_password'):
    error = 'Your passwords do not match.'
```

`if` followed by `elif` (short for “else if”) checks alternatives in order. Only the first matching branch runs. This app reports one validation issue at a time.

**Lines 80–81:** Reject an empty name or one longer than 80 characters. `len(...)` returns the number of characters in the Python string.

**Lines 82–83:** The email test rejects when any of these conditions is true:

| Expression | Meaning |
| --- | --- |
| `len(email) > 254` | Too long for our chosen maximum |
| `email.count('@') != 1` | Not exactly one `@` |
| `not all(email.split('@'))` | A part before/after `@` is empty |
| `'.' not in email.split('@')[-1]` | The domain part contains no dot |
| `any(c.isspace() for c in email)` | At least one character is whitespace |

For `'sam@example.com'`, `.split('@')` produces `['sam', 'example.com']`. `[-1]` picks `'example.com'`. `all(...)` is true if every part is truthy/nonempty. `any(...)` is true if at least one test result is true.

`c.isspace() for c in email` is a **generator expression**: iterate through the characters, naming each `c`, and produce the result of its whitespace test. `any` consumes those results and can stop as soon as it finds one true value.

This is **basic format checking**, not a complete email standards validator. It does not check that a mailbox exists, send a verification email, or reject every malformed address. For example, some bad domain structures can still pass these checks.

**Lines 84–85:** A chained comparison `8 <= len(password) <= 128` means both bounds must be satisfied. `not` reverses that result, so this branch runs when the length is outside the permitted range.

**Lines 86–87:** Reject if the password differs from its confirmation. The confirmation field only helps catch typing mistakes; it is never stored in the database.

Browser `required`, `type='email'`, and length attributes improve usability, but a caller can bypass a browser and send arbitrary HTTP. That is why this backend validation remains necessary.

### Lines 88–98: save the account or return validation feedback

```python
if error is None:
    try:
        db().execute('INSERT INTO users (name, email, password_hash) VALUES (?, ?, ?)', (name, email, generate_password_hash(password)))
        db().commit()
    except sqlite3.IntegrityError:
        error = 'An account with this email already exists. Please log in.'
    else:
        flash('Account created! Log in to get started.', 'success')
        return redirect(url_for('login'))
flash(error, 'error')
return render_template('auth.html', registering=True)
```

This snippet is formatted to match the blocks, but remember the last `return` is outside the POST block in the original function. It handles both initial GET and redisplaying an invalid POST.

**Line 88:** Proceed to insertion only if no validation error was set.

**Line 89:** Begin the database operation that might violate a constraint.

**Line 90:** `INSERT INTO users (...) VALUES (?, ?, ?)` adds one row. The tuple `(name, email, generate_password_hash(password))` supplies the three values in the same order. We omit `id`, allowing SQLite to assign it.

`generate_password_hash(password)` creates a salted password hash representation. The installed Werkzeug version currently uses scrypt by default. The stored string contains information about the algorithm/parameters, salt, and derived hash, allowing `check_password_hash` to verify it later. Use the helper rather than implementing cryptography yourself.

The **salt** is random data generated for each stored password. Consequently, two users choosing the same password normally have different stored hash strings. A password hash is a one-way checkable representation, not encrypted text that the app later decrypts. A slow password hashing function makes mass guessing more expensive; it does not make weak passwords impossible to guess.

See the official [Werkzeug password helper reference](https://werkzeug.palletsprojects.com/en/stable/utils/#module-werkzeug.security) for the helper behaviour and defaults.

The SQL placeholders matter here: name/email/password hash are data. Building SQL by inserting user text directly into the query string could allow SQL injection. This implementation passes values separately to SQLite.

**Line 91:** Commit the insertion. Otherwise a successful-looking request could finish without a persisted account.

**Lines 92–93:** If the database reports `IntegrityError`, display the duplicate-email message. Given the currently validated fields and schema, the expected violation is the email's `UNIQUE` constraint. Technically `IntegrityError` can represent other constraint violations too, so if the schema grows this broad message may need refinement. The database constraint also handles two requests attempting the same email concurrently.

**Line 94:** `else` attached to `try/except` runs when the `try` completed without that exception. It is not the `else` of an `if` here; indentation and placement tell you which structure it belongs to.

**Line 95:** Queue a temporary success message. The category `'success'` becomes a CSS class when displayed. `flash` does not print to the terminal or render the page immediately.

**Line 96:** Redirect to login. This is **Post/Redirect/Get**: process a successful POST, redirect, then display a GET page. Refreshing that final page does not repeat account insertion. Registration does not automatically log the user in.

**Line 97:** For a validation error or duplicate email, queue the error message. Because the success branch already returned, it never falls through to this line.

**Line 98:** Render the shared authentication template with `registering=True`. This keyword argument is a template variable. It tells Jinja to show the name and confirmation fields and use registration wording. On an invalid POST the template restores the submitted name/email, but not passwords.

### Lines 100–112: login

```python
@app.route('/login', methods=['GET', 'POST'])
def login():
    if g.user:
        return redirect(url_for('dashboard'))
    if request.method == 'POST':
        user = db().execute('SELECT * FROM users WHERE email = ?', (request.form.get('email', '').strip().lower(),)).fetchone()
        password = request.form.get('password', '')
        if user and len(password) <= 128 and check_password_hash(user['password_hash'], password):
            session.clear()
            session['user_id'] = user['id']
            return redirect(url_for('dashboard'))
        flash('Email or password is incorrect.', 'error')
    return render_template('auth.html', registering=False)
```

**Line 100:** Register login for GET and POST.

**Line 101:** Define its handler.

**Lines 102–103:** A valid logged-in browser goes directly to dashboard.

**Line 104:** Only attempt credential verification for POST; GET simply displays the form.

**Line 105:** Normalise the submitted email just as registration does, find that account, and return a row or `None`. SQL `SELECT *` means all columns, including `password_hash`, which login needs. Again the value is passed in a one-element tuple using a `?` placeholder.

**Line 106:** Retrieve the exact submitted password, with an empty fallback.

**Line 107:** Login succeeds only if all three checks succeed: the account exists; password length is at most 128; Werkzeug verifies the password against its stored hash. `and` short-circuiting prevents checking a hash on a nonexistent user and avoids hashing needlessly long submitted passwords. A separate minimum-length login rule is unnecessary: a short password cannot match one registered under our existing minimum rule.

We do not generate a fresh salted hash and compare its string with the saved one: a new random salt would normally produce a different string. The checking helper reads the stored hash's parameters/salt and performs the appropriate verification.

**Line 108:** Clear the old session data before establishing the authenticated state. This removes any earlier user ID, CSRF token, and queued messages from that session data. In our default Flask setup, there is no server-side session ID table being rotated.

**Line 109:** Put the database user's ID into the session. This is the central step that establishes login across later requests. Flask signs the updated session cookie and sends it in the response; the browser sends that cookie back on subsequent requests.

**Line 110:** Redirect to the protected dashboard. The next GET request runs `load_user`, loads the record using this ID, and passes the login guard. The dashboard's logout form calls `csrf_token()`, generating a new token after the old session was cleared.

**Line 111:** For failure, use a general message without saying whether the email or password was wrong. The registration duplicate-email message still reveals that an address is registered; the project does not claim complete prevention of account enumeration.

**Line 112:** Render the same template with `registering=False`, so it shows the two-field login form. Invalid login redisplays the form with a message; it does not create session authentication data.

### Lines 114–117: protected dashboard

```python
@app.route('/dashboard')
@login_required
def dashboard():
    return render_template('dashboard.html')
```

**Line 114:** Register the dashboard URL.

**Line 115:** Wrap the handler in our login check. Decorators are applied **from the bottom upward**: `login_required` first produces a guarded function, then `app.route` registers that guarded function. The guard runs on incoming requests, not merely at startup.

**Lines 116–117:** The actual handler renders the dashboard only after the guard passes. Its template uses `g.user` for the greeting and email. Hiding a link in HTML would not protect a route; checking in Python is what prevents direct unauthenticated access.

### Lines 119–124: logout

```python
@app.route('/logout', methods=['POST'])
@login_required
def logout():
    session.clear()
    flash('You have been logged out.', 'success')
    return redirect(url_for('login'))
```

**Line 119:** Accept POST for logout. GET from typing `/logout` into the address bar is not permitted. The shared header submits a small POST form instead. The existing global CSRF check therefore protects it as well.

**Line 120:** Require a current user before executing logout. Anonymous POST requests still encounter the CSRF check before this route guard.

**Line 121:** Define the handler.

**Line 122:** Clear session data, including the user ID. The browser's updated session will no longer authenticate subsequent requests.

**Line 123:** Add a success message. Because this happens after `clear`, the session can still contain data for that message: “logout deletes all browser cookies” would be an inaccurate explanation.

**Line 124:** Redirect to login, where the queued message is displayed. A later dashboard request has no authenticated ID and redirects to login.

There is no server-side session revocation registry in this app. Logging out changes the current browser's cookie; it cannot centrally invalidate a copied older authenticated cookie held elsewhere. More advanced session management is a deployment improvement, not part of this assignment implementation.

Return the Flask object after creating its configuration, initialising the table, and registering its callbacks/routes. This ends `create_app`. The object holds the registered functions and is ready to handle requests.

### Lines 129–130: start only when executed directly

```python

    create_app().run(debug=os.environ.get('FLASK_DEBUG') == '1')
```

**Line 129:** Python sets `__name__` to `'__main__'` when this is the script you execute. If tests instead do `from main import create_app`, its name is `'main'`; therefore this block does not run and import does not launch a web server.

**Line 130:** First call `create_app()` to construct the app, then call `.run(...)` on the returned object to start Flask's development server. It listens on localhost, port 5000 by default. The server keeps running to handle requests until stopped.

`os.environ.get('FLASK_DEBUG') == '1'` is a comparison producing `True` only for the exact environment string `'1'`. This boolean is passed as the `debug` keyword argument. Debug is off by default. Debug mode can reload code and show detailed debugging information, so do not expose it to the public.

This development server is appropriate for a local demonstration. A deployed application needs a production server and deployment configuration. The warning you saw in the terminal does not mean your local app failed.

## 6. Follow one account through the whole application

### Starting the program

1. Python runs imports and defines `create_app`.
2. The direct-execution check at the bottom succeeds.
3. Calling `create_app` creates/configures Flask and the private directory/key.
4. It registers database cleanup, creates the users table if absent, and defines/registers helpers and routes.
5. It returns the app. `.run` starts listening.

Functions are defined and callbacks registered at startup; registration/login bodies are executed later when their requests arrive. Python does not process all routes in order each time a browser loads a page.

### First visit and registration

1. GET `/` has no authenticated session ID, so `load_user` sets `g.user` to `None`.
2. `index` redirects to `/login`; the browser makes another GET request.
3. `login` renders `auth.html` with `registering=False`; Jinja combines it with `base.html`.
4. The template calls `csrf_token()` and inserts that token into the form. Flask's response also carries the signed session cookie containing the expected token.
5. The user follows the registration link, generating GET `/register`; now `registering=True` includes the extra fields.
6. The user submits the form. POST `/register` contains the named field values and hidden token; the browser also sends its cookie.
7. `load_user` verifies the token first. The route then normalises and validates the fields.
8. Werkzeug hashes the password. SQLite inserts the account and commits. No plaintext/confirmation password is saved.
9. Flask queues a message and redirects; GET `/login` displays the account-created message.

### Successful login and later pages

1. POST `/login` submits email, password, and token, with the session cookie.
2. The shared callback checks CSRF.
3. The route looks up the email and verifies its stored password hash.
4. It clears old session contents, stores `user_id`, and redirects with the signed updated cookie.
5. The browser follows with GET `/dashboard` and sends the cookie.
6. `load_user` reads `user_id` from the verified session and loads the row into `g.user`.
7. `login_required` sees a user and allows the view to run.
8. Jinja renders the greeting using the user's name/email. The browser renders the resulting HTML and CSS.
9. New requests repeat the cookie verification/current-user lookup; the user's password is not requested or stored again.

### Logout

1. The header's form submits POST `/logout` with a token.
2. The shared callback checks token and loads user; the login decorator checks authentication.
3. Logout clears session data, queues a message, and redirects.
4. The updated cookie no longer has `user_id`. GET `/login` displays the message.
5. Direct GET `/dashboard` cannot pass the login decorator and redirects back.

The database account remains: logout ends that browser's authenticated state; it does not delete the account.

## 7. Three common sources of confusion

**`request`, `session`, and `g` are not interchangeable.** `request.form` is what this request submitted. `session` carries signed browser state between requests. `g.user` is the user record loaded for this one request. The database persists account records independently of all three.

**A redirect is not a template render.** `render_template` makes HTML for the current response. `redirect` tells the browser to request another URL. The new URL's callback and route run as a new request with a fresh `g`.

**Python source, Jinja expressions, and SQL are different languages.** `if g.user:` is Python; `{% if g.user %}` is Jinja interpreted on the server; `SELECT ... WHERE ...` is SQL interpreted by SQLite; `<input ...>` is HTML interpreted by the browser; `.card { ... }` is CSS interpreted by the browser. The source file containing a string does not determine the language inside that string.

## 8. Why some lines look more advanced than beginner Python

The feature is small, but real web authentication combines several concepts: functions, framework callbacks, contexts, SQL, cookies, password hashing, HTML, and HTTP. You do not need to memorise these lines without understanding their roles.

The most valuable things to be able to explain in your own words are:

1. A browser requests a route; Flask calls the registered Python function.
2. A GET displays the form; a POST submits its named fields.
3. Server validation is necessary even when HTML validates too.
4. Registration saves a salted hash, not the password itself.
5. Login verifies that hash and puts the user's ID in the signed session.
6. Every protected request loads the user and checks the login guard.
7. Logout clears that ID from the browser's current session.
8. Templates generate HTML; CSS determines its presentation.
9. The tests exercise requests and responses without launching a browser.
10. This is an authentication prototype with a dashboard placeholder, not a finished deployed business tracker.
