# Tests, project files, and presenting the app

## Start, stop, and test it

Open the VS Code terminal in the project folder. The existing virtual environment already contains Flask, so this command chooses the correct Python directly:

```powershell
.\.venv\Scripts\python.exe main.py
```

Open **http://127.0.0.1:5000** in a browser. Keep that terminal running. Press **Ctrl+C** in the terminal to stop the server. `127.0.0.1` is your own computer, and `5000` is the port where this server listens. Starting it does not publish a public website.

Run the automated tests in a second terminal, or stop the server first:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

The parts of the command mean:

| Part | Meaning |
| --- | --- |
| `.\.venv\Scripts\python.exe` | Use this project's Python environment. |
| `-m unittest` | Run Python's built-in `unittest` module as a program. |
| `discover` | Find test files automatically. The default filename pattern is `test*.py`. |
| `-s tests` | Start looking in the `tests` directory. |
| `-v` | Print the individual test names and results. |

The suite contains five tests. `OK` means those checks passed. It does not mean every possible behavior or security issue has been tested.

If a teammate clones the project, they create their own environment instead of copying yours:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

The first command needs a working Python launcher. On this computer we created the environment using the installed Python executable because the default launcher was not working correctly. You already have the environment, so use the earlier direct command.

### `.venv/`

A virtual environment isolates this project's installed packages from other Python projects. Its `Scripts/` directory contains `python.exe`, `pip.exe`, and activation scripts; `Lib/site-packages/` contains packages such as Flask, Werkzeug, and Jinja.

Activating an environment adjusts the terminal so `python` and `pip` refer to it. Activation is convenient, but unnecessary when you use the full relative executable path shown above. It does not turn the app into a website by itself.

Do not explain all installed dependency source files as code that you wrote. They are libraries the app uses.

### `__pycache__/`

Python converts source code into an intermediate form called bytecode. `.pyc` files cache that form; they are not your editable source. These files are recreated when needed, which is why Git ignores them.

### `instance/miserly.sqlite`

This is a binary SQLite database, not a Python file or a readable text document. SQLite keeps a database in a local file rather than requiring a separate database server. The current app has one table:

```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL
)
```

| Part | Meaning |
| --- | --- |
| `CREATE TABLE` | Define a table: a collection of rows with named columns. |
| `IF NOT EXISTS` | Leave the existing table alone when the app starts again. |
| `id INTEGER PRIMARY KEY` | Each row has a unique integer identifier. SQLite supplies an ID when the insert does not provide one. This schema does not use the `AUTOINCREMENT` keyword. |
| `name TEXT NOT NULL` | Store text, and reject SQL `NULL` in this column. The Python code separately rejects an empty name. |
| `email TEXT NOT NULL UNIQUE` | Require an email value and prevent duplicate stored email strings. Python lowercases emails before storing and looking them up. |
| `password_hash TEXT NOT NULL` | Store the password hash representation, including the information Werkzeug needs to verify a password. Do not store the original password. |

One row represents one registered account. The confirmation password is used during validation and is never saved. The current schema does not contain business transactions, spending records, roles, or sessions.

This SQL, used by the tests, counts accounts:

```sql
SELECT COUNT(*) FROM users
```

`SELECT` reads data. `COUNT(*)` counts rows. The result is one row containing one number, so `.fetchone()[0]` retrieves that number. The tests execute this against their own temporary databases, not your real accounts.

### `instance/secret_key`

This contains random signing-key text generated on first startup if no `SECRET_KEY` environment variable was supplied. Later starts reuse it. A stable key allows existing signed session cookies to remain verifiable across app restarts.

The key signs cookies; it does not encrypt the database or hash passwords. Keep the actual value private. It is intentionally absent from these guides. The `instance/` ignore rule keeps these runtime files out of new Git commits by default.

## `requirements.txt`: one line

```text
Flask>=3.1,<4
```

This tells pip to install Flask version **3.1 or newer, below 4.0**. Flask in turn declares its own dependencies, so pip installs packages such as Werkzeug and Jinja automatically. Python's standard-library modules, such as `sqlite3` and `unittest`, do not need separate entries here.

The comma combines the two version restrictions. This is a permitted version range, **not a lock file**: two installations on different days may receive different compatible versions. A locked environment would record exact versions for dependencies too.

`pip install -r requirements.txt` means “read package requirements from this file.” `python -m pip` selects the pip associated with that Python interpreter.

## `.gitignore`: every line

Git is the version-control tool that tracks source changes. This file gives Git patterns for files that should remain untracked by default.

| Line | Pattern | Meaning |
| --- | --- | --- |
| 1 | `__pycache__/` | Ignore Python bytecode-cache directories. |
| 2 | `*.py[cod]` | Ignore filenames ending in `.pyc`, `.pyo`, or `.pyd`; `*` matches a filename prefix and `[cod]` matches one of those final letters. |
| 3 | `.venv/` | Ignore the project's generated virtual environment. |
| 4 | `venv/` | Also ignore environments using the alternative folder name `venv`. |
| 5 | `instance/` | Ignore the database and local signing key. |
| 6 | `.env` | Ignore a commonly used filename for local environment settings and secrets. |

There is currently **no code that automatically loads `.env`**. Ignoring that filename does not make it work as configuration. The app reads `SECRET_KEY` and `FLASK_DEBUG` from the process environment using `os.environ`.

An ignore rule does not remove a file that Git already tracks, erase past commits, or prevent someone from manually copying a file. It is a version-control convenience, not encryption or access control.

## What a test does

An automated test is executable code that sets up a situation, performs an action, and checks the result. For example:

1. Make an account in a temporary database.
2. Submit its login form.
3. Check that the response points to `/dashboard`.

The test client acts like a small simulated browser for HTTP requests and cookies. It does not display the page, run browser JavaScript, or check the page's appearance. It can call the Flask app inside the Python process, so the development server does not need to be running.

The app factory makes this practical. Each test creates an independent app configured with a temporary database. Tests do not have to overwrite the real `instance/miserly.sqlite` file.

## `tests/test_auth.py`: imports and the test class

| Line | Code | Explanation |
| --- | --- | --- |
| 1 | `import sqlite3` | Load Python's built-in SQLite support so tests can inspect their database. |
| 2 | `import tempfile` | Load tools for temporary files and directories. |
| 3 | `import unittest` | Load Python's built-in testing framework. |
| 4 | `from contextlib import closing` | Import a helper that closes an object when a `with` block finishes. |
| 5 | `from pathlib import Path` | Import the path-building class. |
| 7 | `from main import create_app` | Import our application factory from `main.py`. Importing it does not start the server because of the `if __name__ == '__main__'` guard in that file. |
| 10 | `class AuthenticationTests(unittest.TestCase):` | Define a class containing the authentication tests. It inherits the assertion methods and test lifecycle from `unittest.TestCase`. |

A **class** defines a kind of object. An **object**, also called an instance, holds data and associated functions. A function defined on a class is a **method**. `self` is the conventional parameter name for the current object. In `self.client`, the client belongs to that test object. Python automatically supplies `self` when we call a method through an instance.

The testing framework finds methods whose names begin with `test_`. The helper methods `post` and `register` do not start with that prefix, so they are used by tests rather than run as separate tests.

### Lines 11–18: prepare and clean up each test

| 12 | `self.temp = tempfile.TemporaryDirectory()` creates a fresh temporary directory and saves the managing object. Its `.name` attribute contains the directory's path. |

| 14 | `create_app({...})` creates the app with a dictionary of test settings. `TESTING=True` enables Flask's testing behavior; `'SECRET_KEY': 'test'` supplies a predictable key only for these tests; `DATABASE` points at the temporary file. ### Lines 20–24: the POST helper

```python
def post(self, path, **data):
    self.client.get('/dashboard' if path == '/logout' else path)
    with self.client.session_transaction() as session:
        token = session['csrf_token']
    return self.client.post(path, data={'csrf_token': token, **data})
```

| Line | Explanation |
| --- | --- |
| 20 | Define our helper, which accepts a URL path and named form values. `**data` collects extra keyword arguments into a dictionary. For `self.post('/login', email='a@example.com')`, `path` is `'/login'` and `data` contains `{'email': 'a@example.com'}`. |
| 21 | First request a page that renders a form and creates a session CSRF token. The conditional expression chooses `/dashboard` for logout because logout has no GET page; otherwise it uses the supplied path. This is a GET request. |
| 22 | Enter a context manager giving the test access to the client's session. `as session` names the object available inside the block. This is a test-only facility, not code the browser executes. |
| 23 | Read the CSRF token the earlier page request placed in the session. Square brackets access a dictionary entry; a missing key would raise an error and expose a problem in this helper/setup. |
| 24 | Submit a POST request with a form dictionary. `{'csrf_token': token, **data}` makes a dictionary starting with the token and adds the other form values. Here `**data` unpacks a dictionary, whereas in the function definition it collected arguments. `return` sends the response back to the calling test. |

We include real CSRF values for normal tests so they reach the behavior under test. The specific CSRF test deliberately bypasses this helper and omits or breaks the token.

### Lines 26–29: the registration helper

| Line | Explanation |
| --- | --- |
| 26 | `def register(self, **changes):` collects optional test-specific changes in a dictionary. |
| 27 | `dict(...)` constructs a default set of form values. These are invented test details. They are not created in the real application database. |

## Assertions and HTTP responses

An **assertion** expresses an expected result. If reality differs, `unittest` marks that test as failed.

| Assertion | Meaning |
| --- | --- |
| `self.assertEqual(actual, expected)` | The values must be equal. |
| `self.assertNotEqual(actual, unexpected)` | The values must differ. |
| `self.assertIn(piece, whole)` | `whole` must contain `piece`. |
| `self.assertNotIn(piece, whole)` | `whole` must not contain `piece`. |

The client returns a response object:

| Attribute | Meaning |
| --- | --- |
| `.status_code` | HTTP status number, such as `200` for a normal page, `302` for a redirect, `400` for a bad request, or `405` for a method that is not allowed. |
| `.location` | The destination in a redirect response. Checking this does not automatically follow the redirect. |
| `.text` | The response body decoded into text, which lets tests search the generated HTML. |

## What the suite does and does not demonstrate

The tests check several important paths, using an independent temporary database per test. They are useful when changing the backend: a later mistake in logout or routing can be caught automatically.

They do not open a real browser, check the CSS layout, test the complete range of allowed input, test concurrency, measure password strength, verify HTTPS behavior, or establish that a public deployment is ready. They also do not test ownership of future spending records because those records do not exist in this implementation yet.

## Honest scope and limitations

For a lecturer, describe this as **the authentication part of a Flask business tracker, with a protected placeholder dashboard**.

- The implemented account features are registration, login, logout, input checks, password hashing, signed cookie sessions, CSRF checks, and escaped HTML output.
- Email checking is basic format checking. It does not confirm that the address exists or belongs to the registrant. There is no verification-email flow.
- There is no password-reset flow, login-attempt rate limit, multi-factor authentication, role system, or “log out all devices” function.
- Length checks do not guarantee a strong password. This is not a breached-password screening system.
- Flask's default session cookie is signed, not encrypted. A person who possesses it can inspect its data, so passwords and secret information must not be stored in it. This app stores the user ID, CSRF token, and flash messages there.
- Logout clears the current client's authentication data. It does not revoke a stolen copy of a previously valid cookie, because there is no server-side session record or revocation list. The following `flash()` call also creates new session data, so “logout deletes every cookie” would be inaccurate.
- The current cookie is `HttpOnly` and `SameSite=Lax`. `HttpOnly` limits JavaScript access to that cookie; it does not remove all risk from malicious scripts. Secure-only cookies and HTTPS are deployment work; the local development server is HTTP.
- The generated CSRF token has no separate timer. A rejected form may have a missing or mismatched token; the error page's “expired” wording is a general message, not a claim that we implemented an individual form expiry clock.
- The development server is suitable for local work. A public deployment needs a production server, stable secret configuration, HTTPS, and other operational protections.
- No spending-entry, purchase-history, reporting, or other business-tracking feature is implemented yet.

These limits do not erase what the project does. They help you state its actual behavior precisely.

## Questions you should be able to answer

**Why use a virtual environment?** Each project can have its own installed packages, and the interpreter path makes it clear which environment is running the app.

**Why SQLite?** It is available through Python's standard library and stores this small local app's data in one file, without a separate database server. Another database may be appropriate as the team and deployment requirements grow.

**Why an app factory?** `create_app()` builds an independently configured Flask application. Tests can supply a temporary database without touching the real accounts.

**Where is the user's password stored?** It is not stored as plaintext. SQLite stores the Werkzeug password-hash representation. The entered password is checked against that representation at login.

**Where is login remembered?** In Flask's signed session cookie in the browser. The user ID is then used to fetch the current account on each request.

**Why do both browser and server validate inputs?** Browser attributes improve the experience, but requests can be sent without a browser. The server must enforce its own rules.

**What does a redirect mean?** The server returns a response telling the browser which URL to request next. It is a new request, not a direct Python call to another route function.

**Why POST for logout?** Logging out changes authentication state, so it is submitted as a state-changing form request, with a CSRF token.

**What is the difference between authentication and authorization?** Authentication identifies who is signed in. Authorization decides what that user may access. The dashboard requires authentication; future business records also need ownership checks.

**What does five passing tests mean?** The five defined tests met their assertions in that environment. It does not prove all behavior, all security, or all deployment requirements.

**What remains for teammates?** Business data models and features, user-specific record access, and any extra account or deployment requirements the team chooses.
